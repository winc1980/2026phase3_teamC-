# 1.コミュニケーション
チーム内で常に情報を共有しましょう。
github、discord、対面の3つの場をうまく使い分けましょう。

### github
githubにはソースコードとタスク、マイルストーンが置かれます。

### discord
タスクの進捗、チームのみんなと一緒に考えたいことなどを共有しましょう。
フォーラムは、各タスクや個別の議題ごとにスレッドを分けて話し合うのに向いています。
VCで会議や作業をするのもおすすめです。

### 対面
一週間に一回の貴重な場です。

自分たちが何を作ろうとしているのか、チームとしてどこに向かっていきたいのかをよく話し合って、開発計画を立てていきましょう。

# 2.マイルストーン
マイルストーンとは、いつまでに何を達成するかの目標です。
phase3では、月ごとのLT会が期限の目安としてちょうどよいでしょう。

githubには、専用の機能"milestones"があります。チームで決めたマイルストーンの内容に合わせて書き込んでみてください。

### 2.1.MVP開発：最小限の実用性を提供する
とにかく最低限使えるものを作ろうという考え方です。
phase3の間に作りきれるように、milestone設定ではこの考え方を意識してください。

# 3.タスク
チームが次に何に取り組むべきことを、タスクとして言語化しましょう。
githubのissueを使って管理していきます。

## 3.1.優先順位を付ける
やることに優先順位を付けなければ、開発を期限内に終わらせることはできません。

ここではMoSCoW分析を紹介します。
| MoSCoW | 優先度 |
| ------ | ------ |
| Must | 必須 |
| Should | 作るべき |
| Could | あるとよい |
| Won't | いらない |

タスクをこれらの4つに分けます。
mustから着手し、時間があれば、should、couldへ広げていきます。

このタスク整理を、マイルストーン単位で定期的に行うことをおすすめします。
今のマイルストーンに必要なタスクに集中して進めていくのが大事です。

### 優先順位をissueのラベル(タグ)にする
決めた優先順位は、githubのissueに **ラベル** として付けておきましょう。
issue一覧やProjectsのボードで、ラベルを使って絞り込めるので、「次に何をやるか」がすぐに分かります。

ラベル名はMoSCoWと対応させるのがおすすめです。チームで話し合って、自分たちにとって一番分かりやすい名前を付けましょう。

| MoSCoW | 例1：そのまま | 例2：高低+closeで表す |
| ------ | ------------- | --------------- |
| Must | `must` | `high` |
| Should | `should` | `middle` |
| Could | `could` | `low` |
| Won't | `won't` | `lowest` |

Won'tの場合は、ラベルを付けずにタスクを閉じると決めてしまうのもおすすめです。

名前は自由ですが、次の2つは守りましょう。

- [ ] チームで1種類の名前に統一する（`must` と `high` が混ざると絞り込みが効きません）
- [ ] 1つのissueに付ける優先順位のラベルは1つだけにする

ラベルはリポジトリの Issues → Labels → New label で作れます。優先度ごとに色を変えておくと、一覧で見分けやすくなります。

## 3.2.タスクを分割する
タスクの完了に必要な作業量、技術的難易度は、タスクによって様々です。
実際にチームで作業に取り組む前に、次のもくもく会までの1週間でできる大きさに分割しましょう。
**作業時間2～3時間、コード100行くらい**が目安です。
さらに小さくて取り組みやすいタスク(good first issue)もあると良いでしょう。
小さなタスクでも、やりきったことが成果として可視化されると達成感があります。

チーム全員がタスクに取り組めている状態を目指しましょう。

### 分担ではなく分割する
タスクは「担当範囲」ではなく、「できあがったら動かして確かめられるもの」で区切ります。

- ○ 「検索機能」→「検索フォームの画面」「検索APIを1本作る」「結果の一覧表示」「0件のときの表示」
- ✗ 「検索機能」→「フロント側」「バック側」

担当範囲で区切ると、終わったときに「自分が何を作ったか」が残りません。
うまく割れたか迷ったら、次の2つで確かめましょう。

- [ ] 作業時間2～3時間に収まるか（超えるなら、もう一段割る）
- [ ] 終わったとき、担当した人が「〇〇を作った」と一言で言えるか

大きい機能は、githubのissueの **sub-issues** 機能を使って親issueと子issueに分けると、全体像と進み具合が見やすくなります。

## 3.3.タスクの依存関係を可視化する
別のタスクがタスク着手の前提になっている場合があります。どの順番で取り組むと良いかを考えましょう。mermaid図の有向グラフを使うのがおすすめです。

``` mermaid
graph LR
    A[タスクA: 要件定義] --> B[タスクB: 基本設計]
    B --> C[タスクC: 実装]
    B --> D[タスクD: テストケース作成]
    C --> E[タスクE: 結合テスト]
    D --> E
    E --> F[タスクF: リリース]
```
